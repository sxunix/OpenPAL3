# 冶炼（SCE 146 `UIShowSmeltingMenu`）

莫子牙的炼妖壶：拿尸块配矿石炼东西。地址都是 PAL3 v1.4 未加壳
`PAL3_unpacked.exe`。

## 1. 入口

`LAB_00436a10`（opcode 146，一个 int 参数）：

```text
FUN_0044f610(3)             // 进模式 3 = 冶炼
DAT_00dba240 = 参数          // 这是个**过程号**，不是「种类」
new 等待任务 FUN_00434ca0(3) → FUN_00434c40   // 脚本挂起到模式结束
```

参数是过程号：**前台菜单的「聊天」钮**（`FUN_0047c430` 的 `param_2 == 0x403`）会
`FUN_00432170(DAT_00dba240, 0)` 把它当脚本跑。实机里只有一处用到这个命令，
Q13 的 proc 1409「莫子牙冶炼」，传的 1410 是「莫子牙聊天」——四段对白，
没有给东西的指令。（先前把 0x403 当成「确认」钮，是看错了对象：`FUN_0047c430` 是
菜单的事件处理，不是冶炼页的。退出钮 0x405 什么过程都不跑。）

## 2. 配方表 `FUN_0047a580`

```text
FUN_0040d010(10)  → 尸块（ItemType 12）
FUN_0040d010(3)   → 矿石或尸块（ItemType 5 或 12）
for 尸块 in 尸块表:
    for 候选 in 矿石表:
        if 尸块.ore_id (物品 +0x308) == 候选.id:
            一条配方：产物 = 尸块.product_id (+0x30c)
```

两张表都是从背包按 id 升序抓的，所以配方的顺序就是背包顺序。行里记的是
尸块 id（`+0x1704`）、矿石 id（`+0x1708`）和两边的数量
（`+0x16fc` 尸块、`+0x1700` 矿石）。

`FUN_0040d010` 的分支号与物品类型：case 3 = type 5 或 12，case 10 = type 12
（同一张 switch 也管道具页和战斗道具页，见 `item_use.md` §2.1）。

## 3. 加入与撤销

- `FUN_0047aab0(行)`：两边数量各减一，**当场从背包里各扣掉一个**
  （`FUN_0040cf60`）。数量减到负数就弹提示、把这一行的两个计数清零。
- `FUN_0047adf0(行)`：撤销，数量各加一，把两样东西还回背包
  （`FUN_0040ccf0`）。
- `+0x2a778` 是已经排进队列的对数（加一/减一）。

## 4. 产物什么时候进背包

**炼够 5 秒才给**，在每帧的 `FUN_0047b3b0`（0x47b3b0）里：

```text
if (this->+0x2a774 == 0) return;              // 没在炼就跳过
if (!this->+0x2a744) { this->+0x2a740 = timeGetTime(); this->+0x2a744 = 1; }
now = timeGetTime();
if (now - this->+0x2a740 <= 0x1388) return;   // 5000 毫秒没到
this->+0x2a740 = now; this->+0x2a744 = 0;
FUN_0047b140(this, this->+0x27c34);           // 显示产物说明
FUN_0040ccf0(&this[(this->+0x27c34 + 0xe4) * 0xc]);   // 产物进背包，数量 1
…弹一句「用 X 和 Y 炼出了 Z」…
this->+0x2a775 = 1; this->+0x2a774 = 0;       // 这一炉结束
this->+0x27c34 = -1;
```

`(行 + 0xe4) * 0xc` 就是 `+0xab0 + 行*0xc` 那个三元组——`FUN_0047a580` 建表
时写的 `{产物 id, 1, 数据库指针}`，正好是 `FUN_0040ccf0` 的入参形状。

`+0x2a774`（正在冶炼）在确认那一支置 1（0x47ba36），火花特效
`FUN_0047b3b0` 的另一半（0x47b200 起）也拿它当闸。**一次确认只出一件**，
给完就把标记清掉、选中行置 −1，中间没有回到发货那一步的分支。

早先在 .text 里按 4 字节位移搜 `0x14f8` 搜不到读的地方，是因为行基址是
`esi + 行*0x31c`，代码用的是 `lea` + 小位移，立即数里根本不出现 0x14f8。
换成「找 `FUN_0040ccf0` 的全部调用点」一下就找到了（0x47b43f）。

### 5.4 开炉的火花（`FUN_0047a400` 撒、`FUN_0047b140` 每帧推、粒子类模式 12 `FUN_004b5d20`）

页面上 60 个 UI 粒子（`+0x2a77c` 起，每个 0x248 字节，粒子类构造 `FUN_004b4690`、析构 `FUN_004b47e0`）。
开炉时 `FUN_0047a400` 全部撒出；之后每帧 `FUN_0047b140`（`+0x2a774` 为 1 时）挨个推：活着的（`+0x80`，
`FUN_004b4830`）调 `FUN_004b4dc0(0xc)` = 模式 12 推一步再画，死了的照撒的参数重撒（这一帧不画）。

撒一颗（rand 调用顺序照原版）：

    x = rand % 50 + 168（撒的范围 +0x3305c..+0x33068 = (168,168,268,328)，50 = 宽/2）
    贴图 Par_Effect\spark.tga，32×32（FUN_004b48e0）
    颜色 FUN_004b4850(R, G, B)：B = rand%10+0xfc、G = rand%10+0x24、R = rand%10+0xdb，写进 +0x7c/+0x7d/+0x7e 三个字节
        ——B 超过 255 的绕回 0..5，所以火花一部分偏品红、一部分偏红
    alpha(+0x7f) = rand % 135 + 120；+0x84 = 1.6（每帧减）；+0x244 = 0.8
    FUN_004b49c0(x, 168)、FUN_004b4b10(100, 160)：活动范围 x0 = x−50、x1 = x+50、上 168、下 168+160
    FUN_004b4d80(10, 2)：+0x90 = 10（横向速度）、+0x94 = 2（初始上升量）
    FUN_004b4da0(rand%8+2, rand%8+2)：+0x9c = 上升速度（后一个 rand 先算），+0x98 模式 12 不用

模式 12 每帧（`FUN_004b5d20`）：

    横向：dx = ftol(+0x90 × +0x244) = 8；状态 +0x60 = 0 往右（过 x1 转 1）、1 往左（到 x0 转 2）、2 往右（到 x1 转 1）
    y = 下 − 上升量；y ≤ 上 + 16 → 升到顶（+0x58 = 1，+0x80 = 0）
    上升量 += +0x9c × 0.8
    alpha = ftol(alpha − 1.6)；≤ 0 → 死（+0x80 = 0，+0x58 = 0）
    活着、或者是淡没的那一帧 → FUN_005407a0(x−16, y−16, x+16, y+16, 颜色, 贴图)

`FUN_005407a0` 传的渲染状态是 `DAT_0189505c`（普通界面贴图 `FUN_00540440` 用 `DAT_0189504c`），`spark.tga` 是黑底无 alpha
的 RGB 图——看样子是叠加 [推断]。移植端 imgui 只有 alpha 混合：贴图亮度当 alpha、颜色填白、乘顶点色，近似叠加；
原版按帧推，移植端按 60 帧每秒折算 [推断]。

3D 预览（§5.2 表里那台相机）载的是这一行的产物：行记录 `+0xab0` 起每行 12 字节 [id, 1, 物品指针]（`FUN_0047a580` 填），
`0x47b455` 取 `+0xab8` 的模型名。
