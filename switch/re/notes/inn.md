# 客栈（SCE 119）

`UIShowHotelMenu`。地址都是 PAL3 v1.4 未加壳 `PAL3_unpacked.exe`。

**一句话**：SCE 119 打开的是「聊天 / 住宿 / 退出」**三项菜单**，不是直接
问要不要住店。点「住宿」才播 `M_Rest` 那句话，播完再弹一次「住宿共需 N
文钱」的是/否，答「是」且钱够，才淡出黑屏、回血扣钱、淡入。

## 1. 入口

分发表 0xd8c464 的第 119 项：handler `0x004369c0`，参数 `string int int int`。

```text
FUN_004369c0：取四个参数 → FUN_0044b630(配置文件, 钱够过程, 钱不够过程, 住完过程)

FUN_0044b630：
    ecx = this + 0x1cfc                  // 配置对象内嵌在客栈对象里
    FUN_0044b8a0(配置文件)                // 解析 DealScript\Rest\*.txt
    +0x2510 = 钱够过程
    +0x2514 = 钱不够过程
    +0x2518 = 住完过程
    虚调用 (*+0x18)(1000, 1, 0)           // → FUN_0044b710，复位 +0xcd8/+0xce8/+0xce9
    FUN_0044b470()                        // 摆好三项菜单并显示
    +0x2528 = 1                           // 「客栈流程进行中」
```

配置对象的基址是 `this + 0x1cfc`，所以配置里的字段在客栈对象上要加这个偏移
（`M_RestPrice` 的 `+0x410` → `+0x210c`，每帧函数读的就是它）。

`FUN_0044b470` 只有一个调用者（`FUN_0044b630`），`FUN_0044b630` 也只有一个
调用者（0x436a02，就是 119 的 handler）——所以这个界面**只为 SCE 119 存在**。

## 2. 三项菜单（`FUN_0044b710`）

`FUN_0044b710(消息, 参数, ...)` 是客栈对象的消息处理。菜单项在
`FUN_0044aeb0` 一带构造，三个按钮控件分别在 `+0x374` / `+0x4cc` / `+0x624`，
按钮 id 用三个相邻字节的地址 `0xaabef7/f8/f9` 顶替，文本取自本地化表：

| 按钮 | id | 控件 | 文本 | AssisLang 槽 |
|---|---|---|---|---|
| 聊天 | 0xaabef7 | +0x374 | `DAT_00dd8f3c` | **348** |
| 住宿 | 0xaabef8 | +0x4cc | `DAT_00dd903c` | **349** |
| 退出 | 0xaabef9 | +0x624 | `DAT_00dd913c` | **350** |

（本地化表基址 0xdc333c、步长 0x100，所以 `0xdd8f3c` → 348。）

消息 0x3e9（点击）的三支：

```text
聊天：放 wa001 音效；+0x73d = 1；FUN_0044b690() 关菜单
      if (+0x2008 != 0) FUN_00432170(+0x2008, 0)    // +0x2008 = M_ID
      关界面。完。

住宿：+0xcd4 = 1                                     // 「该弹确认框了」
      FUN_00451200(+0x2110, 0)                       // 用 M_Rest 播一句话
      +0x73d = 2；FUN_0044b690() 关菜单
      +0x2528 = 1                                    // 重新打开住店流程

退出：+0x73d = 3；FUN_0044b690()；关界面。完。
```

`FUN_0044b690` 除了关掉那几个控件，还会把 **`+0x2528 = 0`**——这一点后面
要紧。

## 3. 每帧流程（0x44b0f0）

Ghidra 没把它识别成函数（导出的 `decompiled.c` 里 0x44b000–0x44b470 之间
是空的），下面是读反汇编读的。

```text
if (+0x2528 == 0) return 0;              // 不在客栈流程里就不管

// —— 一、弹「住宿共需 N 文钱」+ 是/否 ——
if (对话系统空闲 && +0xcd4 != 0) {        // 0x44b12a 是 je，+0xcd4 为 0 就跳过
    格式化 "\n          %s%d%s"           // 0x59daec
        %s = AssisLang 346「住宿共需」
        %d = +0x210c                      // M_RestPrice
        %s = AssisLang 347「文钱」
    FUN_004427c0(缓冲, 0)                 // 上屏
    FUN_004a1530(1)                       // 开是/否控件（+0x77c）
    +0xcd4 = 0
}
```

也就是说：SCE 119 一进来虽然 `+0x2528 = 1`，但 `+0xcd4` 还是 0，确认框不会
弹——**要等玩家在菜单上点了「住宿」**（那一步把 `+0xcd4` 置 1 并播 `M_Rest`）
才轮到它。等对话系统把 `M_Rest` 播完，确认框才出来。

```text
// —— 二、读是/否（FUN_004a1cf0，控件在 +0x77c）——
0 = 住下：
    FUN_0044b690() + 虚调用 (**this)(0)   // 注意：这里 +0x2528 被清成 0
    if (DAT_00c05f54 < +0x210c)           // 钱 < 价格（jge，等于算够）
        +0x2520 = FUN_00432170(+0x2514, 0)   // 跑「钱不够」过程；+0x2528 留在 0
    else
        +0x251c = FUN_00432170(+0x2510, 0)   // 跑「钱够」过程
        +0x2528 = 1;  +0xce8 = 0             // 重新打开，流程继续
1 = 不住：
    FUN_0044b690() + 关界面；+0x2528 留在 0，下一帧就退出

// —— 三、「钱够」那段对白跑完（FUN_004324b0(+0x251c) == 0）——
if (+0xce8 == 0 && +0xce9 == 0) {
    +0xce8 = 1
    +0xcd8 = FUN_004be1a0(FUN_004be590(1))    // 淡出（黑屏）
}

// —— 四、黑屏之后等 1000 毫秒，然后真的住这一晚 ——
if (+0xce8 && 淡出完成 && GetTickCount() − +0xce0 > 0x3e8) {
    回血（见 §4）
    DAT_00c05f54 -= +0x210c                    // 扣钱
    g_story 特判（见 §5）
    +0xcd8 = FUN_004be1a0(FUN_004be590(2))     // 淡入
}

// —— 五、淡入完成 → 跑「住完」过程，清干净 ——
if (+0xce9 && 淡入完成) {
    +0x2524 = FUN_00432170(+0x2518, 0)
    +0x2510/2514/2518/251c/2520/2524 = 0
    +0xce8 = +0xce9 = +0xcd4 = +0x2528 = 0
    关界面
}

// —— 六、「住完」那段对白也跑完 → 再清一次，收工 ——
```

`+0x2520`（钱不够那个过程的句柄）确实从头到尾没被读过，但**流程并不会卡**：
`FUN_0044b690` 已经把 `+0x2528` 清成 0，钱不够那一支没有再置回 1，下一帧
函数开头就 `return 0` 退出了。（先前这份笔记说「会一直空转到场景切换」，
那是把 `FUN_0044b690` 只当成关控件、漏了它清 `+0x2528` 那一句，订正。）

## 4. 住一晚回哪几项（0x44b2d7）

```text
ecx = 0
eax = 0xc0476c                          // 角色 0 的 +0x3cc
do {
    if ((&DAT_00c05f58)[ecx] != 0) {     // 这个角色在队里
        [eax]     = [eax - 0x30]         // +0x3cc = +0x39c
        [eax + 8] = [eax - 0x28]         // +0x3d4 = +0x3a4
    }
    eax += 0x580;  ecx++;
} while (eax < 0xc062ec);                // 五个角色
```

角色表基址 `DAT_00c043a0`、跨度 0x580（和状态页笔记一致）：
`+0x39c/3a0/3a4` 是精/气/神**上限**，`+0x3cc/3d0/3d4` 是精/气/神**当前**。
`0xc0476c − 0xc043a0 = 0x3cc`，对得上。

| 项 | 上限 → 当前 | 住店回不回 |
|---|---|---|
| 精 | `+0x39c` → `+0x3cc` | **回满** |
| 气 | `+0x3a0` → `+0x3d0` | **不回** |
| 神 | `+0x3a4` → `+0x3d4` | **回满** |

中间那一项不是漏读——循环体里就只有那两条 `mov`。`DAT_00c05f58` 是队伍成员
标志数组（宿营那段用的也是它），不在队上的不回。

## 5. 住店会推进剧情（0x44b317）

```text
eax = FUN_004343f0("g_story")            // 0x59dae4
if (eax != 0) {
    if      ([eax+4] == 0x2b5d)   [eax+4] = 0x2bc0;    // 11101 → 11200
    else if ([eax+4] == 0x1d5ed)  [eax+4] = 0x1d5ee;   // 120301 → 120302
}
```

只有这两个值有特判。`g_story` 就是脚本里的全局变量 **−32768**（滑雪那边
M22 proc 1001 的 `13 var-32768, 130400` 用的是同一个）。

## 6. 配置（`DealScript/Rest/*.txt`，`FUN_0044b8a0` 解析）

关键字表在 0x59ba98，节名 `sec1`。七个字段，**只有三个真的被读**：

| 键 | 配置对象内偏移 | 客栈对象上 | 用在哪 |
|---|---|---|---|
| `M_ID` | `+0x30c` | `+0x2008` | **「聊天」跑的过程号**，0 无效 |
| `M_Name` | `+0x30e` | `+0x200a` | 全 exe 无引用 |
| `M_RestPrice` | `+0x410` | `+0x210c` | **价格**，比钱和扣钱都用它 |
| `M_Rest` | `+0x414` | `+0x2110` | **点「住宿」时播的那句话** |
| `M_Enough` | `+0x514` | `+0x2210` | 全 exe 无引用 |
| `M_NoEnough` | `+0x614` | `+0x2310` | 全 exe 无引用 |
| `M_RestEnd` | `+0x714` | `+0x2410` | 全 exe 无引用 |

后四个字段配置里写着，程序一个都没读——对白全靠三个过程号。（扫 `.text`
里 `+0x2210`/`+0x2310` 一处引用都没有；`+0x2410` 命中的 0x5263cc 和
0x528d7e 反汇编下来是 `push ebp` 那串字节和一个 `0x24` 常量，都是巧合。）

### 出厂数据的两处毛病

- **`q01rest2.txt` / `q01res2t.txt` 的 `M_ID` = 1802 接错了**。`Q01.sce` 的
  proc 1802 叫「摘星手套」，不是掌柜的聊天过程。在新安当那家点「聊天」会
  跑到不相干的剧情段去。
- **`q01res2t.txt` 没有任何脚本引用**（名字里 `res2t` 是 `rest2` 的错拼）。
  Q01 里用 119 的只有 proc 1415（`q01rest.txt`）和 1801（`q01rest2.txt`）。
  它是份内容雷同、只有掌柜名不同的废文件。

## 7. 脚本那头长什么样

`Q01.sce` proc 1415「客栈掌柜住宿」整个过程只有一条指令：

```text
119 "DealScript\rest\q01rest.txt", 1418, 1419, 1420
```

三个过程号的命名把语义写死了：

| 过程 | 名字 |
|---|---|
| 1416（`M_ID`） | 客栈掌柜**聊天** |
| 1418（钱够） | 客栈掌柜住宿**1** |
| 1419（钱不够） | 客栈掌柜住宿**2** |
| 1420（住完） | 客栈掌柜住宿**3** |

全实机用 119 的一共 12 处，都是 46–47 字节的单指令过程。

## 8. 移植

- 规则：`states/inn.rs`——三项菜单、回哪两项、钱够的判据（`jge`，等于也算
  够）、剧情号特判、确认框那句话的格式，单测覆盖。配置解析仍是
  `states/shop::RestScript`；菜单和确认框的文本走 `openpal3::assis_lang`。
- 命令：`commands/show_chat_rest.rs`（这之前是个直接 `return true` 的空桩，
  住店不扣钱也不回血）。六个阶段：菜单 → 播 `M_Rest` → 确认 → 淡出 →
  全黑一秒（结算就在这一段末尾）→ 淡入。淡出淡入用引擎的 `curtain`。
- `pal3_inn_census` 拿实机数据核对七项：十三份配置的字段、AssisLang 那五条
  和三个菜单项的绑定、每家 `M_ID` 在本场景里是「XX聊天」（两处出厂缺陷单列）、
  Q01 那一组过程的命名、住店结算（钱正好够 / 差一文）、剧情号只推两个。
- 和原版的差别：
  - **两段对白和黑屏的先后**。原版是「钱够的对白 → 黑屏结算 → 住完的对白」；
    移植端把黑屏和结算放在两段对白**之前**。原因是 vm 在一条命令阻塞期间
    不取新指令（`SceVm::update` 里 `active_commands` 非空就不 `get_next_cmd`），
    命令没法在自己中间等一个 proc 跑完。两段对白的先后仍和原版一致
    （`call_proc` 是压栈，先压「住完」后压「钱够」）。
  - 淡出淡入各 0.5 秒、`M_Rest` 停 2 秒是 **[推断]**：原版的黑屏由
    `FUN_004be590/004be1a0` 那对淡入淡出对象做，时长没读出来；`M_Rest`
    是等对话系统播完，移植端没有那套时序。
  - 界面是 800×600 上的文字浮层，不是 `FUN_0044b470` 那一版。原版的布局
    全部相对对话框算（`+0x5c/0x60` 位置、`+0x74/0x78` 尺寸，控件再各加
    一个偏移），没有硬编码坐标，要复刻得先把对话框那个基类逆出来。
  - 菜单上多画了一行掌柜的名字（`M_Name`）。原版没读这个字段，是移植端
    自己加的抬头。
  - 快进（脚本自动跑图）当作选了「退出」：一个过程都不跑，钱和血都不动。
